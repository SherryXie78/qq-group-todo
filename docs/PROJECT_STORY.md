# 项目简报：我做了什么

## 30 秒介绍

我在校园使用多个群聊时发现，重要通知容易被回复和长文本淹没，因此发起了「Q群消息代办」。我负责梳理需求、决定优先级，并在真实电脑和手机上试用验收。项目基于现成的消息处理引擎，使用 AI 编程工具辅助迭代，把信息整理成可核对原文、可纠错、可分阶段完成的待办。每周日复盘问题，并用代码、测试和验收记录保存改进过程。

## 可以讲的八期内容

| 主题 | 我发现的问题 / 作出的选择 | 实现与可学知识 |
| --- | --- | --- |
| 1. 为什么要做 | 多群消息分散，重复回复影响阅读 | 白名单、过滤、摘要、任务的区别 |
| 2. 阅读更快 | 标题冗长，难以看清要做什么 | 时间 / 地点 / 行动三要素、原文依据 |
| 3. 时间准确 | 今天被归到以后，练习与考试混成一天 | 时区、日期范围、阶段截止时间 |
| 4. 纠错可保留 | 错的是时间或内容，不能直接丢弃任务 | 文本反馈、异步处理、审计、撤销 |
| 5. 避免混合和重复 | 一条通知包含多个作业，同一事项多次通知 | 拆分、候选检索、模型判断、保守合并 |
| 6. 电脑手机一起用 | 单独登录采集曾影响普通电脑 QQ；手机需要私人访问 | 采集与工作台分层、认证、缓存；移动重连仍待排查 |
| 7. 让工具更有趣 | 完成任务缺少反馈 | 积分账本、事务、幂等、头像本地处理 |
| 8. 做成长期作品 | 需要可核查地说明自己做了什么 | Git、Issue、测试、版本说明、隐私检查 |

## 面试时如何说明贡献

可以说：项目发起与需求负责人；负责优先级、使用反馈、验收；基于开源引擎与 AI 编程工具持续开发。

暂时不要说：从零独立手写全部系统、已稳定服务大量用户、已实现关机后全天采集。现阶段没有这些证据。

公开文档不使用真实聊天做案例。演示录像请使用虚构任务，避免拍到账号、二维码、私人地址或原始通知。

## 学习路线

先能解释一条消息如何变成任务，再理解 HTTP 请求与认证、SQLite 表与事务、时间处理、测试和 Git 提交。每周围绕一个真实问题学习一两个概念，比一次背全部术语更实用。
